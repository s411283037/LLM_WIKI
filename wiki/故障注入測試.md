# 故障注入測試

> 測試日期：2026-11-24  
> 測試範圍：餐廳訂位自編案例與 Wiki 到簡報的 Graph  
> 重要說明：本頁記錄的是刻意放入的錯誤，不是正式 Wiki 知識，也不是最終投影片內容。

## 測試目的

確認簡報製作流程能分辨兩種不同錯誤，並退回正確節點：

1. 找到錯誤分店的資料。
2. 找到正確資料，但回答加入來源沒有支持的內容。

測試問題：

> 信義店這週六晚上七點，我們有七位，可以線上預約嗎？還有位嗎？

正式案例來源：[餐廳訂位模擬資料](../examples/restaurant-booking.md)（自編教學示例）。

## 故障注入測試 1：引用錯誤分店

> [!danger] 刻意錯誤，禁止用於正式內容
> 使用 `BOOK-BANQIAO` 回答：「信義店七人可以線上訂位。」

| 紀錄項目 | 結果 |
|---|---|
| 測試輸入 | 信義店、週六 19:00、七人、詢問線上訂位與即時空位 |
| 故意使用的資料 ID | [BOOK-BANQIAO](../examples/restaurant-booking.md#book-banqiao) |
| 發現問題的關卡 | 查詢 Wiki 與案例資料後的證據條件核對 |
| 發現的問題 | 問題指定信義店，證據卻屬於板橋店；分店條件不一致。 |
| Graph 退回節點 | **查詢證據** |
| 必要修正 | 先以分店條件篩選資料，改查 [BOOK-XINYI](../examples/restaurant-booking.md#book-xinyi)。 |
| 修正後說法 | 「信義店 7 人訂位須電話聯絡。」 |
| 複查結果 | 通過。分店、人數門檻與資料 ID 一致。 |

這項測試說明：語意看似相關並不夠，檢索結果還必須符合「信義店」這個精確條件。

## 故障注入測試 2：回答超出正確證據

> [!danger] 刻意錯誤，禁止用於正式內容
> 使用 `BOOK-XINYI` 後回答：「七人須電話聯絡，週六晚上七點還有位。」

| 紀錄項目 | 結果 |
|---|---|
| 測試輸入 | 信義店、週六 19:00、七人、詢問線上訂位與即時空位 |
| 使用的資料 ID | [BOOK-XINYI](../examples/restaurant-booking.md#book-xinyi)、[HOURS-XINYI](../examples/restaurant-booking.md#hours-xinyi)、[AVAILABILITY](../examples/restaurant-booking.md#availability) |
| 發現問題的關卡 | 逐頁稿完成後的逐項主張／忠實度核對 |
| 發現的問題 | `BOOK-XINYI` 只支持訂位方式；`HOURS-XINYI` 只支持營業時段；`AVAILABILITY` 明確表示沒有即時剩餘座位資料。沒有任何證據支持「還有位」。 |
| Graph 退回節點 | **逐頁稿** |
| 必要修正 | 保留受支持的訂位規則與營業時間，將空位說法改為無法確認。 |
| 修正後說法 | 「信義店 7 人訂位須電話聯絡。週六晚上 7 點位於示例營業時間內，但目前沒有即時空位資料，因此無法確認是否還有座位，請向分店確認。」 |
| 複查結果 | 通過。回答中的三個部分分別對應 BOOK-XINYI、HOURS-XINYI 與 AVAILABILITY，沒有推測即時空位。 |

這項測試說明：找到正確來源不代表生成內容一定忠於來源，仍須把回答拆成可逐項核對的主張。

## Graph 驗證結果

```text
錯誤分店資料
→ 證據條件核對失敗
→ 退回查詢證據
→ 改用正確分店資料 ID
→ 複查通過

正確店規＋虛構空位
→ 忠實度核對失敗
→ 退回逐頁稿
→ 刪除無證據主張並明示資料缺口
→ 複查通過
```

兩條預定回退路線皆可攔截對應錯誤。這只能證明檢查設計在本次測試中有效，不能證明系統之後不會出現其他錯誤。

## 實際製作錯誤

### 內容自我稽核發現三筆標示問題

| 紀錄項目 | 結果 |
|---|---|
| 類型 | 3 筆實際製作錯誤，不是故障注入 |
| 發現問題的關卡 | HTML 完成後的內容自我稽核 |
| 發現的問題 | 第 3 頁把專案證據檢查混入 RAG 基本架構；第 6 頁省略 Single DPR 訓練變體；第 9 頁省略 GPT-3.5-Turbo（0613）、多文件問答與 20 份文件條件。 |
| Graph 退回節點 | **逐頁稿／主張核對** |
| 必要修正 | 分離 RAG 核心與專案檢查；補上 Single DPR；補上長上下文實驗的模型、任務與文件數，並區分位置實驗與文件數實驗。 |
| 複查結果 | 通過。三處已回查原始論文並同步修正逐頁稿與 HTML。 |
| workflow 修改 | HTML 製作前新增「架構歸因、實驗變體、模型與任務條件」三項檢查。 |

### HTML 圖表柱狀高度未呈現

| 紀錄項目 | 結果 |
|---|---|
| 類型 | 實際製作錯誤，不是故障注入 |
| 發現問題的關卡 | HTML 渲染截圖檢查 |
| 發現的問題 | 第 9 頁三個位置準確率原本顯示為接近水平線，沒有正確呈現 75.8%、53.8%、63.2% 的高度差。 |
| Graph 退回節點 | **HTML 產生／渲染** |
| 必要修正 | 為圖表欄位補上完整容器高度，使百分比高度能正確計算。 |
| 複查結果 | 通過。重新渲染後三個柱狀均可見，且中間位置最低。 |
| workflow 修改 | 將 clientWidth、scrollWidth 與圖表尺寸的數值檢查放在人工截圖檢查之前。 |

手機截圖一度出現右側裁切，但診斷顯示 Edge 無頭工具實際使用 492 px viewport、只輸出 390 px 寬截圖；活動投影片的 clientWidth／scrollWidth 為 492／492，沒有水平溢出。因此這是測試工具限制，不計為簡報錯誤。

## 與故障注入分開統計

- 本次共有 2 筆故障注入、4 筆實際製作錯誤。
- 逐頁稿／主張核對有 3 筆實際錯誤，是本次執行最常出錯的節點；HTML／渲染有 1 筆。
- 這仍只有一次執行樣本，不能推廣成所有專案長期最常出錯的節點。
- 後續若再修改簡報，新的實際錯誤仍須與兩筆人為測試分開統計。
